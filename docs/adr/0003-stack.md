# ADR-0003: Go + Fiber API, Next.js on Bun, spec-first OpenAPI

Status: Accepted (2026-10-07). The product owner pinned the stack. The contract approach is our decision.

## Context
The frontend (TypeScript) and backend (Go) are written in different languages, and several agents and humans will work on them in parallel. The main integration risk is the two sides drifting apart.

## Decision
- Backend: Go ≥ 1.26, Fiber v3, pgx v5. Frontend: Next.js 16 (App Router) on Bun ≥ 1.3.14.
- `api/openapi.yaml` (OpenAPI 3.1) is the single source of truth:
  - Go server interfaces and models are generated by `oapi-codegen` (strict server).
  - TS types are generated by `openapi-typescript`, and the client is `openapi-fetch`.
- In production, Caddy serves both behind one origin (`/api/*` → Go). This avoids CORS and keeps cookies simple.

## Consequences
- Every API change starts in the YAML file. CI fails when the generated code is stale.
- Check with context7 whether `oapi-codegen` supports Fiber v3. If it doesn't, generate the `std-http` strict server and mount it with Fiber's `adaptor` middleware. Record that choice in a follow-up ADR.
- Authentication lives in Go, so the web app needs no native Node addons. Bun has gaps with some of them.
